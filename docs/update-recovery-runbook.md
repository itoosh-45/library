# עדכון והתאוששות — שלב 17

## לפני עדכון

1. להוריד JSON מלא, לשמור עותק ולבדוק אותו. ״הופק גיבוי״ אינו הוכחת שמירה; Excel אינו גיבוי תמונות/טיוטות.
2. לסיים עריכה, זיהוי וייבוא ולסגור חלונות נוספים. worker מחכה לאישור מפורש, ללא רענון אוטומטי. מפתחות בזיכרון לא נשמרים בגיבוי.
3. לעדכן, לפתוח מחדש ולבדוק ספירות/ספרים/תמונות/השאלות/טיוטות. להשאיר את הגיבוי עד לסיום הבדיקה.

## blocked ו־versionchange

blocked: החיבור שביקש שדרוג ממתין לחלון ישן; סגירת הישן מאפשרת המשך. ״סגירת החיבור בלי איפוס״ מבטלת את הפתיחה בחלון הממתין ואינה מוחקת נתונים. תשובת promise מאוחרת לא מחליפה את מצב הביטול.

versionchange: החלון הישן נשאר עם הטופס, עם dialog נגיש מעל עורך modal, ושמירות חדשות חסומות גם בשכבת transaction (כולל פעולות async מאוחרות). להעתיק טקסט שלא נשמר לפני שחרור החיבור. אין הבטחה שהטיוטה נשמרה אוטומטית. לאחר שחרור וסיום השדרוג בחלון השני אפשר לפתוח מחדש.

## כשל ושחזור

לא לנקות אחסון, למחוק DB או להקטין גרסה. כשל migration בתוך version transaction מחזיר נתונים וגרסה קודמת; לתקן קדימה ולהריץ שוב. במקרה קובץ פגום, מקור הנתונים נשאר ללא שינוי. להשתמש בגרסת קוד שתומכת במסד; לא להסיק מהצלחה של Dexie.open שתאימות הוכחה. Dexie עשוי לפתוח מסד חדש יותר לאחר VersionError, ולכן האתחול בודק את גרסת IndexedDB native לפני כתיבה.

אם נדרש שחזור: לפתוח יעד נפרד, לייבא JSON בסקירה, לשמור גיבוי מגן של היעד ולאשר החלפה/מיזוג. לבדוק ספרים, קשרים, בתים/hash של תמונות, השאלות וטיוטות. לבדוק שהמקור נשאר זמין. מקור אישי לא נמחק בתרגיל.

## מעבר כתובת/שם ריפו

IndexedDB שייך ל־origin ולשם DB הקבוע `itoosh-45.library.personal.v1`, לא לנתיב הריפו. localhost ו־127.0.0.1 הם origins נפרדים גם באותו מחשב/פורט. שינוי נתיב באותו origin ושם DB משתמש באותה ספרייה; כל אפליקציות Pages באותו username.github.io חולקות origin. לא לשנות שם DB בלי מסלול העברה מפורש.

מעבר דומיין/דפדפן/מכשיר: export מהמקור, import ביעד, אימות וחזרה למקור. אין העתקה אוטומטית בין origins. נתיב פריסה חדש דורש base/start_url/scope/assets תואמים: Vite base מוחלט (`/library/`, `/renamed/` או `/`) משמש ל־HTML, assets ורישום worker; manifest משתמש בכתובות יחסיות אליו. caches מופרדים לפי נתיב בלי ששחרור מעטפת הנתיב החדש ימחק את הישן. שם DB נשאר קבוע. שינוי id היחסי של ההתקנה דורש בדיקה/התקנה חדשה; אין הבטחה לקיצור דרך ישן. יש לסיים עריכה בחלונות ישנים ולהסיר התקנה/רישום worker ישן רק לאחר אימות גישה וגיבוי. בדיקת production מקומית לשני נתיבים אינה הוכחת פריסת Pages בשם חדש. Safari ומצב standalone דורשים בדיקת מכשיר בפועל.

לשחזור בסביבת הפיתוח, מתוך המאגר, לאחר התקנת התלויות הרגילה:

```powershell
New-Item -ItemType Directory -Force private/phase17-previous | Out-Null

```

