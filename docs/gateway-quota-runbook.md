# מכסות קטלוג עמידות — תיקון שער 18

מוני gateway היו בזיכרון והתאפסו בהפעלה מחדש. כל ספק מופעל דורש כעת SQLite מקומי עמיד; חסר/כשל באחסון חוסם לפני קריאת ספק. השירות עדיין loopback בלבד: אין authentication ציבורי או שינוי n8n.

`CATALOG_QUOTA_DB` חייב להיות נתיב מוחלט לקובץ ב־volume מקומי עמיד. תיקיית האב חייבת להתקיים. כל תהליכי השירות משתמשים באותו קובץ ובאותן מכסות מאושרות; אין עותק counter לכל process. אין להציב אותו ב־Pages, build ציבורי, Git, tmp או volume שמתאפס עם restart. אין טענה לתמיכה ב־NFS או שרתים עם דיסקים נפרדים.

Node 24 כולל SQLite: נעשה שימוש ב־DatabaseSync בלי dependency או התקנה חדשה. [תיעוד Node](https://nodejs.org/download/release/v24.20.0/docs/api/sqlite.html). `BEGIN IMMEDIATE` מבצע בדיקה וצריכת slot באותה transaction; `synchronous=FULL` ו־WAL נבחרו לשימור הרישום. נשמרים provider, יום UTC, ספירה וזמן המתנה בלבד. אין key, URL, תמונה, טקסט חיפוש או ספרייה.

המכסה נצרכת לפני קריאת ספק, גם אם הפנייה נכשלת או הלקוח מתנתק. אין refund או retry אוטומטי. לפני בקשה נשמרת חסימה שמרנית ל־24 שעות. תשובה תקינה ומאומתת מחליפה אותה בהמתנת עשר שניות; 429 מחליף אותה ב־Retry-After (לפחות עשר שניות). קריסה, timeout, ביטול, פלט לא תקין או כשל בכתיבת תוצאת הבקשה משאירים חסימה גם אחרי restart. זו פגיעה מכוונת בזמינות במצב לא ודאי. עד שתי בקשות פעילות גלובלית ובקשה אחת לכל ספק; יום חדש מאפס ספירה אך אינו מוחק זמן המתנה. חזרה ליום קודם חוסמת.

אין למחוק/להחליף/להחזיר לאחור את קובץ המכסה כדי לעקוף מגבלה. ההוכחה היא restart עם אותו קובץ שנשמר, ולא מפעיל שמשחזר counter ישן, משנה גבולות או מאבד volume. Retry-After חריג שלא ניתן לרשום כזמן בטוח משאיר חסימת 24 שעות ולא מאומת מול ספק חי. לקראת חשיפה ציבורית נדרשים גם מנגנון הרשאה וסגירת מגבלות התשתית. אין חיוב/אשראי/חידוש/הוספת קרדיטים.

אין להפעיל ספק חי ללא key, מכסה ו־mapping מאומתים. NLI נשאר gated על `NLI_MAPPING_VERIFIED=true`; Books דורש key ו־daily limit חיובי. בלי ספקים health יכול לעבוד ללא קובץ מכסה. הפעלת ספק בלי `CATALOG_QUOTA_DB` מפסיקה startup לפני listen. אין fallback בזיכרון. SIGINT/SIGTERM סוגרים שרת וחיבורים, ואז ledger.

בדיקות quota.test.ts: תהליכי Node עצמאיים צורכים שני slots ונחסמים בגבול; שני תהליכים מתחרים מקבלים reservation אחד; בקשה בלתי גמורה נשארת חסומה; reopening ומעבר חצות משמרים Retry-After; ספק אחר מופרד; clock rollback, state פגום, היעדר אחסון וכתיבת סיום שנכשלת אינם פונים לספק שוב. HTTP fixtures אינם ספק חי. Node 24.19.0 ו־SQLite 3.53.3 נבדקו ב־Windows. fixtures תחת private/phase18-quota-test מכילים ספירות סינתטיות בלבד.

סקירה בחמישה צירים: נכונות — reservation עמיד לפני פנייה, ללא refund ושחזור יום/המתנה; קריאות — ledger קטן נפרד; ארכיטקטורה — SQLite בשירות בלבד, בלי שינוי DB לקוח; אבטחה — fail closed, transactions ושגיאות בטוחות; ביצועים — פעולות סינכרוניות קטנות, לכל היותר שניית המתנה לנעילה, ללא benchmark ציבורי או dependency חדשה. ניסוי סקירה אחד שינה `used >= dailyLimit` ל־`used > dailyLimit`: שתי בדיקות נכשלו. הקוד הוחזר ועשר בדיקות quota/server עברו.

חבילה סופית: npm run check עבר עם 178 Vitest, ארבע Node, טיפוסים/lint ובניית האפליקציה והשירות. בדיקה נוספת של .gateway-dist/run.js בתהליך Node עצמאי עם key סינתטי מוכיחה שהגדרת ספק ללא CATALOG_QUOTA_DB מפסיקה לפני listen ואינה מדפיסה key. אין ריצה חוזרת של 49 browser/9 PWA: frontend/assets נשארו זהים לבנייה הקפואה שנבדקה, והתיקון הוא בשירות בלבד.

T26 Oracle/n8n עדיין NOT RUN. תהליכי Node מקומיים אינם הוכחת Oracle, authentication ציבורי, ניתוק חשמל או storage host שלא נבחר. staging הישן הוא frontend קפוא; אינו מאמת gateway חי חדש.
